Lab 4 Exercise - Cross Validation

Author

Josh Davis/Lucas Schwengber

Learning goals

By the end of this lab you should be able to:

  1. Explain the fundamental reason why cross validation is needed, and why it almost always works better than using training error as a model selection technique.
  2. Explain why training error is not unbiased for the risk. It is too optimistic, because the same data is used to fit and to evaluate the model, and this gets worse as model complexity grows.
  3. State what CV error estimates. If implemented correctly, CV error is unbiased for the expected risk of a model trained on \(N - N/K\) points (under the condition of no distribution shift). Because the final model is trained on all \(N\) points, CV error slightly overestimates its risk.
  4. State the principles required for CV to actually work: the validation data must not be used in training, and it must be distributed like the data the model will be used on. For IID data, a random train-val split achieves this.
  5. Describe how the sizes of the training and validation sets affect the bias and variance of the error estimate.
  6. Describe how the number of folds \(K\) affects the bias and variance of the risk estimate, and the computational burden. Larger \(K\) lowers bias and increases computational burden. The effect on variance is not monotone, which is why \(K = 5\) or \(10\) is common.

Setup

In Parts 1-5 you will work in a simulated “practice world”: a binary classification problem in which we know the true probability \(p(\boldsymbol{x}) = P(y = 1 \mid \boldsymbol{x})\). This means that for any fitted model \(\hat f\) that predicts probabilities \(q(\boldsymbol{x})\), we can compute its true risk (expected log loss on a new observation) exactly, \[ \text{Err}_\mathcal{T} = \mathbb{E}_{\boldsymbol{x}}\left[-p(\boldsymbol{x}) \log q(\boldsymbol{x}) - (1 - p(\boldsymbol{x})) \log (1 - q(\boldsymbol{x}))\right], \] where \(\mathcal{T}\) denotes the training set \(\hat f\) was fit on. We can then check how well training error, validation error and cross validation error estimate it. In real life you never get to do this, which is why we use a simulation.

You are given four files:

  • simulator.py - the practice world (Parts 1-5)
  • X_train.npy, y_train.npy, X_test.npy - the challenge data (Part 6)

The simulator gives you:

  • true_risk(model) - the true risk \(\text{Err}_\mathcal{T}\) of a fitted model. It averages the formula above over 20,000 new feature vectors from the same distribution, which the model never saw. This is the log loss on a huge test set, with each label replaced by its true probability to remove label noise.
  • bayes_risk() - the smallest possible risk, achieved by predicting \(p(\boldsymbol{x})\) itself.
NoteGradient boosting and LightGBM in a nutshell

The model in this lab is a gradient boosted ensemble of decision trees. You do not need the details. Think of it as a flexible black box whose complexity is controlled by hyperparameters, which is exactly when cross validation is needed.

  • Decision tree. Splits the feature space into rectangles with a sequence of yes/no questions such as “is \(x_3 > 0.7\)?”, and predicts a constant in each rectangle (a leaf).
  • Boosting. Instead of one big tree, add many small trees one at a time. Each new tree is fit to correct the errors the current ensemble still makes on the training data (formally, it is fit to the negative gradient of the loss, hence gradient boosting). The sum of the trees is a log odds \(F(\boldsymbol{x})\), turned into a probability by \(q(\boldsymbol{x}) = 1 / (1 + e^{-F(\boldsymbol{x})})\).
  • LightGBM is a fast and widely used implementation of gradient boosting.
Hyperparameter Meaning Larger value gives a model that is
min_child_samples minimum number of training observations in a leaf simpler
n_estimators number of trees more complex
learning_rate how much each new tree’s correction counts more complex

n_estimators and learning_rate trade off against each other: a smaller learning rate needs more trees.

3 When CV breaks

CV works when the validation data is distributed like the data the model will be used on and was not used in training. Each of the two experiments below breaks one of these principles.

  • Experiment B: duplicated observations. Sometimes the same unit appears more than once in a dataset, for example two measurements of the same patient.
  • Experiment A: data that arrives sorted. Real data files are often sorted, for example by label.

6.1 Allowed methods

You may only use lgb.LGBMClassifier, with any hyperparameters you like, trained only on X_train and y_train. The simulator comes from a different distribution, so drawing extra data from it will not help you.

6.2 How to submit predictions

Submit a binary .npy file containing a one-dimensional numpy array of predicted probabilities (numbers between 0 and 1), whose length is the same as the number of rows in X_test:

np.save("pred_{codename}.npy", pred)

The name of the file should be "pred_{codename}.npy" where {codename} is a secret codename of your group’s choosing, that you will be able to use later to identify your submission in the leaderboard.

6.3 How your predictions will be scored

Your predictions will be compared against the real y_test using average log loss: \[ \text{your loss} = -\frac{1}{N}\sum_{n=1}^N \left( y_n \log \text{pred}_n + (1 - y_n) \log (1 - \text{pred}_n) \right). \]

A leaderboard will be published with every group’s codename alongside its loss on the test set, ranked from low to high. No other identifying information will be shared. Your rank on the leaderboard will not factor into your grade in any way.

LLM usage policy

You may use auto-completion for filling out small code snippets (affect around 2-3 lines of code) and documenting your code. Small code snippets are things like “add a label for the axis of the plot”, “change the color of the points”, “add an argument for the number of interactions in the fit”. These are small code operations which do not involve significant planning nor automated changes to the logic of the code without your supervision. All edits must be verified and accepted manually, and you should make sure you know what the code is doing.

Things that are explicitly not allowed are major edits to the code (affect > 10 lines) and ones which involve automating huge parts of the development of the logic structure of your analysis. For example, “write a function to extract features from the data”, or “run a test set validation loop and report the best model”.

Delegate to language models only things which you know exactly how you would have done it yourself or would be comfortable googling/asking for help from someone who already took the course/knows how to code, but who cannot do the learning for you.
